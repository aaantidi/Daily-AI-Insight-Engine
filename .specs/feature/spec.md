# 需求规格文档 — Daily AI Insight Engine (MVP)

> **版本**: 1.0.0
> **状态**: 初稿
> **对应阶段**: Phase 2 — Specify
> **前置文档**: Phase 1 — 需求拆解（6 模块）
> **后续文档**: Phase 3 — plan.md + tasks.md

---

## 1. 概述

### 1.1 项目背景

"Daily AI Insight Engine"（AI 舆情分析日报系统）是一个数据驱动的 AI 行业洞察引擎。其核心使命是：从每日全球 AI 新闻信息中，经过结构化处理与分析，生成一份可读、可追溯、可可视化的"AI 分析日报"。

### 1.2 项目目标

- 将分散的非结构化 AI 新闻转化为结构化、可查询的数据资产
- 通过分批处理和逐条抽取，保证每条信息的分析质量
- 生成含数据支撑、趋势判断、机会风险标注的日报
- 提供可视化图表，帮助读者 30 秒把握当日 AI 动态

### 1.3 项目范围

| 包含 | 不包含 |
|:----|:-------|
| 从静态 JSON 文件读取原始新闻数据 | 实时爬虫或 RSS 轮询 |
| 逐条 LLM 结构化抽取（实体/分类/情感/风险） | 将原始数据一次性丢给 LLM 的"暴力摘要" |
| 聚合统计与 Top-3 热点识别 | 深度自定义查询或数据仓库 |
| 四维趋势推演（技术/应用/政策/资本） | 多语言支持（仅中英文） |
| SVG 图表 + Mermaid 可视化 | 动态交互式图表 |
| CLI 入口的管道编排 | Web UI 或 API 服务 |

### 1.4 数据来源约定

数据源由用户（人类）提供，存放在 `data/raw/` 目录下的静态 JSON 文件中。系统不负责数据采集，仅处理已提供的数据。至少 10-20 条中英文混合数据。

## 2. 用户故事

### US-1: 日报读者 — 快速把握当日 AI 动态

> 作为一名 AI 从业者/投资者/关注者，我希望每天收到一份结构化的 AI 日报，能在 30 秒内了解今日最重要的事件、趋势和风险，以便快速做出技术选型或投资判断。

### US-2: 日报读者 — 深入了解特定事件

> 作为一名日报读者，当我对某个热点事件感兴趣时，我希望能够查看该事件的深度分析（背景、影响、关联事件），并且每一条结论都能追溯到原始新闻来源，以便评估信息的可信度。

### US-3: 系统运营者 — 监控管道运行状态

> 作为一名系统运营者，我希望通过 CLI 一键运行整个数据处理管道，并能查看每个阶段的处理状态（成功/失败/跳过）、耗时和处理数量，以便快速定位问题。

### US-4: 系统运营者 — 处理失败与异常

> 作为一名系统运营者，当管道部分阶段失败时，我希望系统不会整体崩溃，而是优雅地跳过失败项、记录详细错误日志，并在最终报告中说明哪些数据未纳入分析，以便我决定是否需要重新处理。

### US-5: 数据分析师 — 追溯分析结论

> 作为一名数据分析师，我希望日报中的每一条分析结论都附带有数据来源引用（`[ref: {id}]`），并且所有引用的原始结构化数据可在索引中查找到，以便验证分析的准确性和完整性。

### US-6: 数据分析师 — 验证结构化抽取质量

> 作为一名数据分析师，我希望系统对每条新闻的结构化抽取结果标注置信度评分，并将低置信度（<0.6）的条目标记为需复核，以便我能够识别并人工修正不可靠的抽取结果。

## 3. 功能需求

### 3.1 模块 M1 — INGEST（数据摄入）

**职责**: 从 `data/raw/` 读取原始新闻 JSON，清洗验证，输出标准化的 `RawNewsItem[]`。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F1.1 | 从 `data/raw/` 目录下的 `.json` 文件读取原始新闻数据 | P0 |
| F1.2 | 验证每条数据必填字段完整性（`title`、`content`、`source`、`published_at`） | P0 |
| F1.3 | 缺少必填字段或 `content` 长度 < 50 字符的条目标记为 `status: "skipped"`，记录跳过原因 | P0 |
| F1.4 | 按 `source.type`（tech_media / official / social_media / aggregator）分组统计 | P1 |
| F1.5 | 去重：基于标题+来源的相似度检测并标记重复数据 | P2 |
| F1.6 | 输出标准化 `RawNewsItem[]` 到 `data/structured/{date}/raw_items.json`，附带处理摘要 | P0 |

**输入/输出契约**:

```typescript
// 输入: data/raw/*.json 数组
interface RawNewsItem {
  id: string;                    // 唯一标识符
  title: string;                 // 原始标题
  content: string;               // 正文内容或摘要
  source: {
    name: string;                // 来源名称
    type: "tech_media" | "official" | "social_media" | "aggregator";
    url: string;
  };
  published_at: string;          // ISO 8601
  language: "zh" | "en" | "mixed";
}

// 输出摘要
interface IngestSummary {
  date: string;
  total_input: number;
  validated: number;
  skipped: number;
  skipped_reasons: Array<{ id: string; reason: string }>;
  source_distribution: Record<string, number>;
}
```

### 3.2 模块 M2 — EXTRACT（结构化抽取）

**职责**: 逐条调用 LLM 对标准化新闻进行结构化抽取，输出 `StructuredInsightItem[]`。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F2.1 | 逐条处理：每条 `RawNewsItem` 独立发起一次 LLM 调用，严禁多条混合 | P0 |
| F2.2 | 按顺序抽取：实体识别 → 分类 → 情感判断 → 风险评估 → 影响评分 | P0 |
| F2.3 | 输出字段：entities（companies/products/people/technologies）、topics、category、sentiment、risk_level、impact | P0 |
| F2.4 | 每个 AI 生成字段附带 `confidence`（0.0-1.0）评分 | P0 |
| F2.5 | `extraction_confidence < 0.6` 的条目标记 `needs_review: true`，填写 `review_reason` | P0 |
| F2.6 | `extraction_confidence < 0.4` 时使用低置信度补救 Prompt 自动重试一次 | P1 |
| F2.7 | 英文源新闻强制填充 `title_zh` 字段 | P0 |
| F2.8 | `risk_level >= medium` 时必须填写 `risk_rationale` | P0 |
| F2.9 | 结果校验：实体非空、topic 非空、abstract ≤120 字、significance_score 1-10 | P0 |
| F2.10 | 输出到 `data/structured/{date}/items.json`，需复核项写入 `needs_review.json` | P0 |
| F2.11 | 写入 `extraction_summary.json`（总数、成功数、需复核数、平均置信度、耗时） | P1 |

**分批约束**: 逐条处理，最多并行 3 条 LLM 调用。

### 3.3 模块 M3 — SYNTHESIZE（洞察合成）

**职责**: 基于结构化数据进行统计聚合、热点识别、深度分析、趋势推演、机会风险识别，生成 Markdown 日报。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F3.1 | **统计聚合（纯计算）**: 话题频次排名、来源分布、情感分布、风险分布、显著性 Top-10 榜单、实体共现矩阵 | P0 |
| F3.2 | **热点识别（轻量 AI）**: 基于统计数据识别 Top-3 热点事件，输出排名理由和关联条目 ID | P0 |
| F3.3 | **深度分析（逐热点 AI）**: 对每个 Top 热点独立调用 AI 生成深度分析（背景/关键进展/影响分析/关联事件） | P0 |
| F3.4 | **趋势推演（综合分析 AI）**: 从技术/应用/政策/资本四维推演趋势，每个维度至少 2 条数据支撑 | P0 |
| F3.5 | **机会风险识别（AI）**: 基于 `risk_level >= medium` 条目识别风险与机会，提出建议 | P1 |
| F3.6 | **日报组装（纯拼接）**: 将上述结果组装为 Markdown 日报，结构包含概览面板/Top-3/深度分析/趋势推演/机会风险/附录 | P0 |
| F3.7 | 所有分析结论使用 `[ref: {id}]` 标注数据来源 | P0 |
| F3.8 | 数据不足时（总条目 < 10）输出低置信度警告；总条目 = 0 时不生成日报 | P1 |
| F3.9 | 矛盾信息处理：同一热点下不同新闻给出矛盾信号时，标注分歧 | P2 |

**分批约束**: 按话题分组，每组 ≤10 条；顺序处理，先聚合再分析。

**日报结构**:

```
# AI 分析日报 — YYYY-MM-DD
## 概览面板 (Dashboard)
## 第一部分: Top 3 焦点事件
## 第二部分: 重要事件深度分析
## 第三部分: 趋势推演 (四维雷达)
## 第四部分: 机会与风险提示
## 附录 A: 数据来源与方法论
## 附录 B: 完整结构化数据索引
```

### 3.4 模块 M4 — VISUALIZE（可视化生成）

**职责**: 生成 SVG 图表（柱状图/饼图/雷达图）+ Mermaid 时间线，嵌入日报。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F4.1 | **话题热度柱状图（SVG）**: 展示 Top-10 话题频次，水平柱状图，降序排列 | P0 |
| F4.2 | **情感分布饼图/环形图（SVG）**: 展示正面/中性/负面比例，色盲友好配色 | P0 |
| F4.3 | **显著事件时间线（Mermaid timeline）**: 按时间排列 Top-10 显著事件 | P0 |
| F4.4 | **趋势四维雷达图（SVG）**: 展示技术/应用/政策/资本四维 confidence 值 | P0 |
| F4.5 | 所有 SVG 包含 title、legend、数据来源标注、时间戳 | P0 |
| F4.6 | 可选图表：实体共现网络图（Mermaid）、风险仪表盘（SVG）、来源分布环形图（SVG） | P2 |
| F4.7 | 输出到 `.specs/daily-report/assets/` 目录，日报中引用 | P0 |

**SVG 质量标准**:
- `viewBox="0 0 800 500"` 统一画布
- 内联 `<style>` 定义样式
- 颜色方案使用项目色板
- 所有标签正确闭合

**分批约束**: 按图表类型分组，可并行生成不同图表。

### 3.5 模块 M5 — Pipeline（管道编排）

**职责**: 编排四阶段（INGEST → EXTRACT → SYNTHESIZE → VISUALIZE），提供 CLI 入口，分级日志。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F5.1 | 提供 CLI 入口：`npm run daily` 或 `npx daily-insight` 一键运行全管道 | P0 |
| F5.2 | 支持指定日期运行：`npm run daily -- --date=2026-06-01` | P1 |
| F5.3 | 四阶段顺序执行，每个阶段完成后输出状态摘要 | P0 |
| F5.4 | 支持阶段级重跑：`npm run daily -- --stage=extract` | P1 |
| F5.5 | 分级日志系统：`[DEBUG]` / `[INFO]` / `[WARN]` / `[ERROR]` / `[FATAL]` | P0 |
| F5.6 | 部分失败处理：失败项跳过，成功项继续，最终报告说明失败情况 | P0 |
| F5.7 | 管道整体耗时统计，各阶段耗时明细 | P1 |
| F5.8 | LLM API 调用重试机制：最大 3 次，Exponential Backoff（1s → 2s → 4s） | P0 |
| F5.9 | 不可重试错误（401/403/400）直接失败，标记条目状态 | P0 |

### 3.6 模块 M6 — Models（共享数据模型）

**职责**: 定义全管道共享的 TypeScript 类型和 Zod schema，确保数据一致性。

| 功能编号 | 描述 | 优先级 |
|:---------|:-----|:------|
| F6.1 | 定义 `RawNewsItem` 接口和 Zod schema（输入阶段用） | P0 |
| F6.2 | 定义 `StructuredInsightItem` 接口和 Zod schema（抽取阶段输出） | P0 |
| F6.3 | 定义 `IngestSummary`、`ExtractionSummary`、`AggregationStats` 等中间产物类型 | P0 |
| F6.4 | 定义 `TopEvent`、`DeepAnalysis`、`TrendAnalysis`、`RiskOpportunityPanel` 等分析产物类型 | P0 |
| F6.5 | 定义 `DailyReport` 最终日报类型 | P1 |
| F6.6 | 所有 Zod schema 必须能对 LLM 输出进行运行时校验 | P0 |
| F6.7 | schema 版本管理：Major/Minor 版本号，向后兼容策略 | P2 |

**Schema 设计原则**:
1. **原子性**: 每个字段表达一个单一事实
2. **可查询性**: 字段设计使得"今天 AI 安全相关的新闻有哪些？"可通过过滤而非全文搜索回答
3. **可追溯性**: 保留指向原始数据的引用
4. **置信度透明**: 每个 AI 生成字段附带置信度

## 4. 非功能需求

### 4.1 性能

| 编号 | 需求 | 指标 |
|:-----|:-----|:-----|
| N1.1 | 单条新闻 LLM 抽取耗时 | ≤10 秒（3.5 Sonnet 模型） |
| N1.2 | 全管道运行时间（20 条数据） | ≤5 分钟 |
| N1.3 | 纯计算阶段（统计聚合、日报组装）耗时 | ≤2 秒 |
| N1.4 | 并行抽取最大并发数 | 3 条 |

### 4.2 可靠性

| 编号 | 需求 | 指标 |
|:-----|:-----|:-----|
| N2.1 | LLM API 调用失败自动重试 | 3 次，退避时间 1s/2s/4s |
| N2.2 | 单条数据处理失败不影响整体管道 | 优雅跳过，记录日志 |
| N2.3 | Zod schema 校验拦截 | 不合规的 LLM 输出被拒绝并重试 |
| N2.4 | 重试耗尽后日志记录 | 写入 `status: "failed"` + `error_reason` |

### 4.3 可维护性

| 编号 | 需求 | 指标 |
|:-----|:-----|:-----|
| N3.1 | TypeScript 严格模式 | `strict: true` |
| N3.2 | 测试覆盖率 | ≥80% |
| N3.3 | 模块化架构 | 6 个模块之间通过类型接口通信，低耦合 |
| N3.4 | Prompt 模板集中管理 | 所有 prompt 存放在对应 `skills/*/prompts.md` 中 |

### 4.4 可追溯性

| 编号 | 需求 | 指标 |
|:-----|:-----|:-----|
| N4.1 | 每条分析结论引用原始数据 ID | `[ref: {id}]` 格式 |
| N4.2 | 数据 ID 全局唯一 | `{source_abbr}-{date}-{seq}` 格式 |
| N4.3 | 结构化数据保留指向原始数据的引用 | `source.url` 字段 |
| N4.4 | 所有 LLM 调用记录保留 | 日志中记录 prompt 模板版本和响应 |

### 4.5 可访问性

| 编号 | 需求 | 指标 |
|:-----|:-----|:-----|
| N5.1 | SVG 图表颜色方案色盲友好 | 不使用仅靠颜色区分的标注 |
| N5.2 | 图表中关键信息有文字标注 | 数据值直接显示在图表上 |
| N5.3 | 日报语言 | 中文为主，关键术语保留英文原名 |

## 5. 验收标准

### US-1: 日报读者 — 快速把握当日 AI 动态

- [ ] 日报包含概览面板，展示新闻总数、情感分布比例、风险条目数量、Top 话题标签
- [ ] 日报列出 Top-3 热点事件，每个事件有排名、标题、重要性评分和排名理由
- [ ] 日报包含四维趋势推演（技术/应用/政策/资本），每维度有趋势判断和置信度
- [ ] 总字数在 2000-4000 字范围内（不含附录）
- [ ] 关键数字使用加粗或突出显示
- [ ] 专业术语在首次出现时有解释

### US-2: 日报读者 — 深入了解特定事件

- [ ] 每个 Top-3 热点事件附带深度分析，包含事件背景（200-400 字）、关键进展（3-5 条）、影响分析（短期/中期）、受影响方
- [ ] 每条深度分析中的结论均有 `[ref: {id}]` 引用标注
- [ ] 所有引用的 ref ID 在附录 B 的完整索引中能找到
- [ ] 日报附带可视化图表（柱状图/饼图/时间线/雷达图），帮助直观理解

### US-3: 系统运营者 — 监控管道运行状态

- [ ] CLI 命令 `npm run daily` 可一键执行完整管道
- [ ] 管道运行过程中输出每个阶段的起始、结束、耗时和状态
- [ ] 管道结束时输出整体统计：总处理条数、成功/失败/跳过数量、总耗时
- [ ] 支持 `--date` 参数指定处理哪天的数据
- [ ] 支持 `--stage` 参数从指定阶段开始执行

### US-4: 系统运营者 — 处理失败与异常

- [ ] 当某条数据抽取失败时，管道继续处理下一条，不整体崩溃
- [ ] 失败条目记录到日志中，包含条目 ID、错误类型、失败原因
- [ ] 最终报告中注明："今日共获取 X 条信息，其中 Y 条成功处理，Z 条因 [原因] 未纳入分析"
- [ ] LLM 调用重试 3 次仍失败后，正确标记该条为 failed
- [ ] 原始数据全部为 0 时，输出"今日无可分析数据"并不生成日报

### US-5: 数据分析师 — 追溯分析结论

- [ ] 日报中每一条分析结论都有至少一条 `[ref: {id}]` 数据支撑
- [ ] 附录 B 包含当日所有条目的结构化数据索引（id、title、source、URL）
- [ ] 不存在无数据支撑的断言或空洞形容词堆砌
- [ ] Top-3 排名与统计聚合数据不矛盾（如排名第一的热点对应最高频话题）

### US-6: 数据分析师 — 验证结构化抽取质量

- [ ] 每条结构化数据包含 `extraction_confidence` 字段
- [ ] 低置信度条目（<0.6）的 `needs_review` 字段为 `true`
- [ ] 低置信度条目附带明确的 `review_reason`
- [ ] `data/structured/{date}/needs_review.json` 文件中汇总所有需复核条目
- [ ] 每条记录至少识别出一个实体（companies/products/people/technologies 任一非空）
- [ ] 每条记录至少包含一个 topic 标签

## 6. 边界约束

### 6.1 技术栈约束

| 约束 | 说明 |
|:-----|:------|
| 语言 | TypeScript（严格模式） |
| 运行时 | Node.js ≥ 18 |
| LLM API | Anthropic Claude API（3.5 Sonnet / 4 Sonnet 等） |
| 测试框架 | Jest |
| 数据校验 | Zod |
| 可视化输出 | SVG + Mermaid（纯文本，不依赖外部渲染库） |
| CLI | Node.js 原生（无额外 CLI 框架依赖可选） |

### 6.2 数据处理约束

| 约束 | 说明 |
|:-----|:-----|
| 数据量 | 每批次至少 10 条，建议 10-20 条 |
| 数据源 | 用户提供，从静态 JSON 文件读取 |
| 单批上限 | 20 条/天（MVP 范围） |
| 语言 | 中文和英文，中英文混合数据 |
| 数据源类型 | tech_media / official / social_media / aggregator |

### 6.3 LLM 调用约束

| 约束 | 说明 |
|:-----|:-----|
| 分批处理 | 逐条抽取，严禁一次性将所有原始数据丢给 LLM |
| 抽取粒度 | 1 条/LLM 调用 |
| 并行上限 | 最多 3 条同时抽取 |
| 合成粒度 | 按话题分组，每组 ≤10 条 |
| 重试策略 | 最多 3 次，Exponential Backoff（1s/2s/4s） |
| 可重试错误 | 网络超时、429、5xx |
| 不可重试错误 | 401、403、400（schema validation error 除外） |

### 6.4 输出约束

| 约束 | 说明 |
|:-----|:-----|
| 日报字数 | 2000-4000 字（不含附录） |
| 图表数量 | 至少 4 个必须图表 |
| 图表格式 | SVG 矢量（柱状图/饼图/雷达图）+ Mermaid（时间线） |
| 引用约束 | 每条分析结论至少一个 `[ref: {id}]` |
| 证据约束 | 趋势判断每维度 ≥2 条数据支撑 |

## 7. 术语表

| 术语 | 英文 | 定义 |
|:----|:-----|:-----|
| 数据摄入 | INGEST | 管道第一阶段，负责读取和清洗原始数据 |
| 结构化抽取 | EXTRACT | 管道第二阶段，逐条调用 LLM 抽取结构化字段 |
| 洞察合成 | SYNTHESIZE | 管道第三阶段，聚合分析生成日报内容 |
| 可视化 | VISUALIZE | 管道第四阶段，生成 SVG/Mermaid 图表 |
| 原始新闻条目 | RawNewsItem | 未经处理的原始新闻数据，含 title/content/source 等 |
| 结构化洞察条目 | StructuredInsightItem | 经 LLM 抽取后的结构化数据，含 entities/topics/sentiment 等 |
| 置信度 | Confidence | AI 生成字段的确定性评分，0.0-1.0 |
| 需复核 | needs_review | 置信度过低时需要人工复核的标记 |
| 显著性评分 | significance_score | 事件重要性评分，1-10 |
| 风险等级 | risk_level | 事件风险级别：none/low/medium/high/critical |
| 重试退避 | Exponential Backoff | 失败重试时逐次增加等待时间的策略（1s→2s→4s） |
| 四维趋势 | Four-dimension Trend | 技术/应用/政策/资本四个维度的趋势分析 |
| 分批处理 | Batching | 将数据分拆为多个小批次处理，避免一次性大量输入 |
| Mermaid | — | 基于文本的图表语法，可嵌入 Markdown |
| SVG | — | 可缩放矢量图形，用于数据可视化 |
| Zod | — | TypeScript 优先的 schema 声明和验证库 |
